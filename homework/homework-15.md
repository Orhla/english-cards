### Г2 — Заголовок `Content-Disposition`

Этот заголовок говорит браузеру, что делать с ответом:

- `Content-Disposition: inline` — показать в браузере (дефолт для картинок, pdf и т.п.).
- `Content-Disposition: attachment` — скачать как файл, не показывать.
- `Content-Disposition: attachment; filename="cat.ogg"` — скачать и предложить такое имя.

Загвоздка с `filename="..."`: значения HTTP-заголовков — это latin-1 (ASCII). Если `originalName` содержит кириллицу, пробелы, кавычки, скобки — `filename="кот (1).ogg"` либо сломается, либо имя придёт кракозябрами.

Решение — расширенный синтаксис из RFC 5987, параметр `filename*` (со звёздочкой):

```
filename*=UTF-8''<percent-encoded-имя>
```

Разбор по частям:
- `UTF-8` — charset, в котором закодировано имя.
- `''` — пустое поле языка (между двумя апострофами; нам язык не нужен).
- дальше — само имя, **percent-encoded** (как в URL): `encodeURIComponent(file.originalName)`.

Пример: имя `кот.ogg` →
```
Content-Disposition: attachment; filename*=UTF-8''%D0%BA%D0%BE%D1%82.ogg
```

**Лучшая практика — отдавать оба параметра сразу:**

```ts
const asciiFallback = file.originalName.replace(/[^\x20-\x7E]/g, "_"); // грубый ASCII-фолбэк
headers.set(
  "Content-Disposition",
  `attachment; filename="${asciiFallback}"; filename*=UTF-8''${encodeURIComponent(file.originalName)}`
);
```

Старые клиенты возьмут `filename=`, современные — `filename*=` (он приоритетнее по спеке).

Мелочи:
- `encodeURIComponent` не кодирует `!'()*` — по строгой букве RFC их надо бы тоже, но для учебного проекта достаточно `encodeURIComponent`. Если хочешь по уму — добавь ручную замену этих символов.
- В `originalName` пользователь мог засунуть что угодно (переносы строк, `"`), а это уходит в заголовок. Не помешает почистить управляющие символы и кавычки перед вставкой. На путь к файлу это не влияет (там `id`), но заголовок лучше не ломать.

### Г3 — Почему не клиентский хак

В PR объясни одной-двумя фразами, почему не пошли путём «на клиенте `fetch` файла → `blob` → `<a download>`»:
- грузим весь файл в память вкладки;
- лишний код на клиенте ради того, что HTTP умеет одним заголовком;
- для больших файлов — совсем плохо;
- всё равно нужен серверный доступ к хранилищу, эндпоинт никуда не девается.

Бонус-мысль для PR: `/api/files/[id]` — единственное место, которое знает, как читать из хранилища. Когда переедем на S3 — этот хендлер сможет просто редиректить на подписанный URL, а форма и весь остальной код не изменятся. Ради этого вся возня с сервисным слоем и затевалась.

- Форма: `register` снят с файловых инпутов, состояние — объекты `{id, originalName}` в памяти RHF, отображение через `watch`, добавить/убрать/скачать до сабмита не трогает сервер.
- Сабмит присылает финальный список id; сервер заменяет связи `WordCardFile` целиком в одной транзакции.
- Скачивание идёт через `/api/files/[id]` с корректным `Content-Disposition` (оба параметра `filename` и `filename*`).
- Orphaned-файлы чистятся cron-джобом раз в сутки — из хранилища и из БД; эндпоинт закрыт секретом.

## Осознанные упрощения (в силе с ДЗ14)

- Все файлы публично доступны без проверки прав — авторизации на скачивание нет.
- Именно поэтому `id` файла обязан быть непредсказуемым (`uuid`, не autoincrement).
- Данные не мигрируются — существующие `audioPath`/`imagePath` просто выпилены вместе с колонками.
- Нет владельца у файла — загружает только админ.
- Хранилище пока локальное (`./storage`), папки создаются руками. Переезд на внешнее хранилище и создание папок на билде — отдельная история (см. ДЗ13-деплой), архитектура под это уже готова: меняется один файл `file-storage.ts`.
