## Часть 1 — Яндекс провайдер

Сейчас весь HTTP-запрос к Яндексу живёт прямо в `enrichWordCard` — экшне. Экшн не должен знать как именно работает Яндекс API, какие у него заголовки и как разобрать ответ. Это не его зона ответственности.

**Создай файл `src/lib/yandex/provider.ts`**

Этот файл — единственное место в проекте где знают про HTTP-детали Яндекс LLM API. Он ничего не знает про слова, карточки, темы — только про протокол.

Функция провайдера принимает всё что нужно для запроса и возвращает разобранный текст ответа:

```ts
export async function callYandexLLM(params: {
  modelUri: string
  messages: { role: "system" | "user"; text: string }[]
  jsonSchema?: object
  temperature?: number
}): Promise<string>
```

Внутри:
1. Достаёт `YANDEX_LLM_API_KEY` и `FOLDER_ID` из констант — проверяет что они есть, иначе бросает ошибку
2. Делает POST-запрос (код запроса переезжает сюда из `actions_yagpt.ts`)
3. Проверяет что ответ `ok`, иначе бросает ошибку
4. Возвращает `alternatives[0].message.text` — строку

Провайдер **не парсит JSON** — он возвращает сырую строку. Что с ней делать — знает тот кто вызывает провайдер.

### Ретраи

Яндекс GPT иногда отвечает с ошибкой — сервер перегружен, таймаут, и т.д. Чтобы не сыпаться при первой же неудаче, добавь в провайдер ретраи.

Логика простая: попробуй сделать запрос, если упал — подожди немного и попробуй снова. Несколько попыток — если все упали, бросай ошибку.

```ts
// примерная структура — детали реализации за тобой
async function callWithRetry(fn: () => Promise<string>, maxAttempts: number): Promise<string> {
  // ...
}
```

Подумай:
- Сколько попыток достаточно? (3 — обычная практика)
- Сколько ждать между попытками? Фиксированное время или нарастающее?
- Какие ошибки стоит ретраить, а какие нет? (Если Яндекс вернул 401 — повторять смысла нет)

## Часть 2 — Агент

Теперь в `actions_yagpt.ts` всё ещё много логики: промпт, схема, разбор JSON, работа с темами. Всё это относится к конкретной задаче — "обогатить карточку слова". Это не задача экшна.

**Создай файл `src/lib/yandex/agents/wordCardEnrichmentAgent.ts`**

Агент — это объект (или функция) у которого зашиты три вещи:
- **промпт** — что мы просим Яндекс сделать
- **схема** — какой JSON мы ожидаем в ответе  
- **логика вызова** — как собрать запрос и разобрать ответ

Агент вызывает провайдер из части 1 и возвращает уже типизированный результат — не строку, не `any`, а конкретный объект.

Схему (которая сейчас лежит прямо в экшне) переноси сюда. Промпты из `src/lib/prompts.ts` — тоже.

### Валидация через Zod

Мы не можем доверять тому что вернул Яндекс — даже если схема в запросе правильная, LLM иногда ошибается. Сейчас код делает просто `JSON.parse(text)` и кастит через `as YandexGPTResponse` — это небезопасно.

Подключи [Zod](https://zod.dev) и опиши схему через него:

```ts
import { z } from "zod"

const WordCardEnrichmentSchema = z.object({
  meanings: z.array(z.string()).min(1).max(3),
  // ... остальные поля
})
```

После `JSON.parse` вызови `WordCardEnrichmentSchema.parse(parsed)` — он либо вернёт провалидированный объект нужного типа, либо бросит ошибку если что-то не то.

Обрати внимание: отдельный TypeScript-тип `type WordCardEnrichment = { ... }` больше не нужен. Zod умеет выводить тип прямо из схемы:

```ts
type WordCardEnrichment = z.infer<typeof WordCardEnrichmentSchema>
```

Это и есть правильный способ — одно место, одно определение. Меняешь схему — тип обновляется автоматически.

Подумай: зачем нам и JSON Schema в запросе к Яндексу, и Zod-валидация на выходе? Разве одного недостаточно?

## Часть 3 — Кэширование `getAllTopics`

Агент при каждом вызове обращается к базе за списком тем — чтобы передать их в схему и промпт. Список тем меняется редко: добавили тему в сид-файл, применили миграцию — и всё, месяцами одно и то же. Гонять запрос к базе при каждой генерации расточительно.

Добавь простое in-memory кэширование прямо в функцию `getAllTopics` в `src/actions/actions.ts`.

Идея: при первом вызове сходить в базу и сохранить результат в переменную модуля. При следующих вызовах — вернуть из кэша, если он не устарел. Через какое-то время (TTL — time to live) кэш "протухает" и следующий вызов снова идёт в базу.

Структура примерно такая:

```ts
let cache: { value: string[]; expiresAt: number } | null = null
const CACHE_TTL_MS = 60 * 60 * 1000 // 1 час

export async function getAllTopics(): Promise<string[]> {
  if (cache && Date.now() < cache.expiresAt) {
    return cache.value
  }
  // ... запрос к базе
  // cache = { value: ..., expiresAt: Date.now() + CACHE_TTL_MS }
}
```

## Часть 5 — Контролируемая форма и обработка ошибок

Две независимых правки в `AdminCardForm`.

### 4а — Убери setTimeout

Сейчас после автозаполнения meanings есть такой код:

```ts
setMeaningCount(otherFields.meanings.length);

setTimeout(() => {
    otherFields.meanings.forEach((meaning, index) => {
        const input = meaningRefs.current[index];
        if (input) {
            input.value = meaning;
        }
    });
});
```

`setTimeout` здесь — это хак: мы ждём "следующего тика" чтобы React успел добавить нужное количество инпутов в DOM после `setMeaningCount`. Форма неуправляемая (`defaultValue` + `ref`), поэтому React не знает про наши значения.

Реши это по-другому: переведи поля `meaning` на управляемый стейт — `useState` с массивом строк. Тогда `setMeaningCount` не нужен вовсе — просто обновляй массив, и React сам нарисует нужное количество инпутов с нужными значениями.

```ts
const [meanings, setMeanings] = useState<string[]>(card?.meaning ?? [""])
```

После автозаполнения — просто `setMeanings(otherFields.meanings)`. Без `ref`, без `setTimeout`.

Сделай то же самое для `translation` и `example`.

### 4б — Покажи ошибку пользователю

Сейчас если `enrichWordCard` упал — ошибка уходит только в `console.error`:

```ts
} catch (error) {
    console.error("Ошибка при автозаполнении:", ...)
}
```

Пользователь нажал кнопку, ждёт, ничего не происходит — и не знает почему.

Добавь `useState` для состояния ошибки и покажи сообщение в UI. Не нужно ничего сложного — просто строка под кнопкой если что-то пошло не так.
