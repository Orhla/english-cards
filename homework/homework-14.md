# Домашнее задание 14

Переделываем работу с файлами (аудио и картинки). Сейчас путь к файлу считается по слову (`${word}.ogg`) и пишется прямо в `WordCard.audioPath`/`imagePath` при сабмите формы. Это хрупко и небезопасно (обсуждали в ревью ДЗ13) — переименовал слово, поменял регистр, ввёл спецсимвол — и путь на диске разъезжается с тем, что в базе.

Идея новой схемы:

1. У файла — своя модель в БД: сгенерированный id, путь на диске, оригинальное имя, MIME-тип, бизнес-тип (аудио/картинка), метаданные (размер, когда загружен).
2. Файл загружается на сервер **сразу**, как только пользователь выбрал его в инпуте — не дожидаясь сабмита формы. В форму подставляется не сам файл, а его id.
3. Форма показывает: что было прикреплено изначально, что изменилось (добавили/убрали), даёт скачать каждый файл, и только по кнопке "Сохранить" эти изменения фиксируются на карточке.
4. Раз файл живёт в БД сам по себе, до того как его прикрепили к карточке — нужно решить проблему "подвисших" файлов: юзер загрузил файл и закрыл вкладку, не нажав "Сохранить".

Договорились на созвоне о серии упрощений для учебного проекта — они специально перечислены в блоке "Осознанные упрощения" в конце. Прочитай его до начала работы, это часть задания, а не просто заметка.

Блок А — первым, он готовит почву для остальных.

## Блок А — Модель файла

### А1 — Добавить модель `File` в Prisma

Нужны поля:
- `id` — **не autoincrement**. Используй `@default(cuid())` (как у `User.id`) или `@default(uuid())`. Почему не просто число — обсудим в блоке Д.
- `path` — путь на диске. Генерируется сервером (например, `${file.id}.${ext}`), никогда не строится из пользовательского ввода.
- `originalName` — как файл назывался у пользователя на компьютере. Нужен, чтобы при скачивании отдать человеку файл с понятным именем, а не `f3a1c9.ogg`.
- `mimeType` — тип файла (`audio/ogg`, `image/webp`, ...).
- `businessType` — свой enum: `audio` | `image`. Нужен, чтобы отличать, куда положен файл (`AUDIO_DIR` vs `IMAGE_DIR`) и какой валидации он подвергался.
- `size` — размер в байтах.
- `createdAt` — когда загружен. Пригодится в блоке Д для чистки.

### А2 — Связь с `WordCard`

У слова — **одно аудио, но несколько картинок**. Это значит, что связь несимметричная. Два способа это сделать, выбери сама и обоснуй выбор в PR одной фразой:

**Вариант 1 — прямые FK, без промежуточной таблицы:**
```prisma
model WordCard {
  // ...
  audioFileId String?
  audioFile   File?   @relation("CardAudio", fields: [audioFileId], references: [id])
  images      File[]  @relation("CardImages")
}

model File {
  // ...
  wordCardId String?
  wordCard   WordCard? @relation("CardImages", fields: [wordCardId], references: [id])
}
```
Просто, но у `File` появляется поле `wordCardId`, которое имеет смысл только для картинок (для аудио связь идёт в обратную сторону, через `audioFileId` на `WordCard`) — то есть модель файла знает о своём использовании чуть больше, чем хотелось бы.

**Вариант 2 — связующая таблица (более общий подход):**
```prisma
model WordCardFile {
  id           Int      @id @default(autoincrement())
  wordCardId   Int
  fileId       String
  businessType businessType // audio | image — здесь, не в File

  wordCard WordCard @relation(fields: [wordCardId], references: [id], onDelete: Cascade)
  file     File     @relation(fields: [fileId], references: [id], onDelete: Cascade)
}
```
`File` вообще не знает о карточках — универсальная модель файла, которую в будущем можно переиспользовать где угодно. За правило "одно аудио на слово" в этом случае отвечает код (или `@@unique([wordCardId, businessType])`, если хочешь довести до предела — но тогда подумай, как это сочетается с "несколько картинок").

Подумай: какой вариант проще реализовать сейчас, и какой не придётся переделывать, если завтра появится третий тип файла (например, видео-пример произношения)?

Убери старые поля `audioPath`/`imagePath` из `WordCard` — миграцию существующих данных в новую модель делать не нужно (см. упрощения).

## Блок Б — Немедленная загрузка файла

### Б1 — Server Action `uploadFile`

```ts
async function uploadFile(file: File, businessType: "audio" | "image"): Promise<{ id: string, originalName: string }>
```

Делает всё то же самое, что раньше делали `saveAudioFile`/`saveImageFile`:
- Проверяет тип файла (`ALLOWED_AUDIO_TYPES`/`ALLOWED_IMAGE_TYPES` уже есть в `consts.ts`) и размер (`MAX_AUDIO_FILE_SIZE_IN_BYTES`/`MAX_IMAGE_FILE_SIZE_IN_BYTES`) — в зависимости от `businessType`.
- Генерирует **свой** путь на диске на основе `id` файла (не имени пользователя, не слова — слово тут вообще ещё может быть не заполнено или не сохранено).
- Пишет файл в `AUDIO_DIR`/`IMAGE_DIR`.
- Создаёт запись `File` в БД: `wordCardId`/связь пока не проставлены — на этом этапе файл не знает и не должен знать, к какой карточке он относится.
- Возвращает `id` (и, например, `originalName` — форме нужно показать, что за файл прикреплён).

Важно: раньше валидация файла происходила в момент сабмита всей формы. Теперь она происходит на **этом** шаге — раньше, при выборе файла. Ошибку неверного формата/размера пользователь должен увидеть сразу, не заполнив остальную форму.

### Б2 — Подключить к инпутам в форме

`onChange` у `<input type="file">` — не дожидаясь сабмита формы, вызывает `uploadFile` и сохраняет полученный `id` в состоянии формы (список для картинок, одно значение для аудио). Пока файл грузится — покажи что-то вроде спиннера/disabled на инпуте.

## Блок В — Форма: состояние и отображение

### В1 — Показать текущее состояние

Форма при открытии карточки на редактирование должна явно показывать:
- Есть ли уже привязанное аудио (имя файла, ссылка на скачивание, кнопка "убрать").
- Список привязанных картинок — то же самое, но списком.

### В2 — Добавление/удаление до сабмита

Пользователь может убрать уже привязанный файл или добавить новый — всё это происходит только в состоянии формы, ничего не отправляется на сервер до нажатия "Сохранить". Если пользователь убрал файл из списка, а потом закрыл форму без сохранения — на сервере ничего не должно измениться.

### В3 — Скачать файл

Ссылка/кнопка "скачать" у каждого прикреплённого файла — ведёт на путь файла, отдаёт оригинальное имя через заголовок `Content-Disposition` (не `f3a1c9.ogg`, а как файл назывался у пользователя).

## Блок Г — Сабмит: полная замена состояния

Это ключевой момент, не пытайся делать diff "что добавилось / что удалилось" на клиенте.

При сабмите форма отправляет **финальный список id файлов**, которые должны быть прикреплены к карточке — прямо как будто это новое состояние с нуля. Сервер (`wordCardFormAction`):

1. Получает `audioFileId?: string` и `imageFileIds: string[]`.
2. Прописывает связи (`audioFileId` на карточке / записи в `WordCardFile`) по этому списку.
3. Всё, что было прикреплено раньше, но не попало в новый список — просто отвязывается (запись `File` не удаляется сразу и физически). Она станет orphaned и будет вычищена по правилам блока Д.

Пример из разговора: у карточки было 2 картинки, пользователь убрал одну и добавил сверху 3 новые — при сабмите на сервер уходит 4 id, и это принимается как полное новое состояние. Сервер не должен пытаться понять "что именно изменилось" — он просто заменяет список.

### Г1 — Обработай ситуацию "файл почищен раньше времени"

Если фоновая чистка (блок Д) успела удалить файл раньше, чем пользователь нажал "Сохранить" (например, файл провисел без дела больше суток, а пользователь как раз в эту секунду отправляет форму) — `id` из формы будет ссылаться на несуществующий `File`. `wordCardFormAction` должен вернуть внятную ошибку ("файл больше не существует, загрузите заново"), а не падать с 500.

## Блок Д — Чистка "подвисших" файлов

Файл считается **orphaned**, если он загружен (`uploadFile`), но так и не был прикреплён ни к одной карточке (или был отвязан на сабмите) дольше **24 часов** с момента загрузки.

### Д1 — Cron-эндпоинт

Создай Server Action / route handler, который:
1. Находит все `File`, у которых нет привязки к `WordCard` и `createdAt` старше 24 часов.
2. Для каждого — удаляет физический файл с диска **и** запись в БД. Оба шага обязательны: если удалить только запись, файл останется висеть на диске мусором.

### Д2 — Расписание через Vercel Cron

В `vercel.json`:
```json
{
  "crons": [
    { "path": "/api/cron/cleanup-files", "schedule": "0 3 * * *" }
  ]
}
```
Раз в сутки, ночью. На Hobby-плане это максимум, что доступно (не чаще раза в день), и точное время не гарантируется — может сработать с задержкой до часа. Для чистки суточного мусора этого достаточно.

### Д3 — Защити эндпоинт

Vercel Cron — это просто HTTP-запрос на публичный URL по расписанию. Значит этот путь (`/api/cron/cleanup-files`) технически доступен снаружи любому, кто его узнает — не только крону. Заведи `CRON_SECRET` в переменных окружения и проверяй его в хендлере (Vercel сам передаёт секрет в заголовке `Authorization`, если он у тебя настроен — почитай в доке Vercel Cron Jobs как именно). Без этой проверки кто угодно может дёргать чистку файлов вручную по прямой ссылке.

## Осознанные упрощения (обязательно прочитать)

Мы сознательно срезаем углы, потому что это учебный проект. В реальном проде так делать нельзя не подумав — но здесь это нормально, если понимать, что именно упрощено:

- **Все файлы публично доступны без проверки прав.** Никакой авторизации на скачивание — кто угодно, у кого есть прямая ссылка, может скачать файл.
- **Именно поэтому id файла обязан быть непредсказуемым** (`cuid`/`uuid`, не autoincrement) — это отдельная гарантия от "публичности". Публичный файл с угадываемым id = кто-то может перебором утащить вообще все файлы с сервера. Публичность и непредсказуемость id — два разных решения, они друг друга не заменяют.
- **Данные не мигрируются.** Существующие `audioPath`/`imagePath` из ДЗ13 просто выпиливаются вместе с колонками. В реальном проекте пришлось бы писать миграцию, которая для каждой существующей карточки создаёт запись `File` из уже лежащего на диске файла — мы этого делать не будем.
- **Нет multi-tenant/владельца у файла.** Загружает только админ, поэтому не храним "кто загрузил" как значимое бизнес-поле (хотя метаданные о времени загрузки нужны для очистки).

## Что должно получиться

- Есть модель `File` с id, путём, оригинальным именем, MIME-типом, бизнес-типом и метаданными.
- Выбор файла в форме сразу загружает его на сервер и получает id — до сабмита формы.
- Форма показывает исходное состояние прикреплённых файлов, позволяет добавлять/убирать, скачивать каждый, и всё это до сабмита не трогает сервер.
- Сабмит присылает финальный список id и полностью заменяет состояние привязки (без diff-логики на клиенте).
- Файлы, загруженные, но не прикреплённые дольше 24 часов, чистятся раз в сутки cron-джобом — с диска и из БД.
- Cron-эндпоинт защищён секретом.
- Обработана ситуация, когда файл из формы был почищен до сабмита.
